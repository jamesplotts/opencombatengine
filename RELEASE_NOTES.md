# Release Candidate 1 (v0.6.0-rc1)

This release marks a significant milestone for the **OpenCombatEngine**, introducing advanced AI behaviors, loot generation, and full Open5e content integration.

## Key Features

### 🧠 Advanced AI System
- **Tier 1 (Zombie)**: Basic "Move & Attack" logic for simple creatures.
- **Tier 2 (Tactical)**: Smart targeting (focus on weak/low HP enemies) and self-preservation logic.
- **Tier 3 (Role-Based)**: Specialized behaviors like "Artillery" (Kiting/Ranged superiority).

### ⚔️ Item Library & Loot
- **Standard Item Library**: Integration with Open5e to fetch Weapons, Armor, and Magic Items.
- **Procedural Loot Generation**: Generate CR-appropriate treasure bundles including Gold/Silver/Copper and Items based on rarity probabilities.
- **Unified Interfaces**: `IItem`, `IWeapon`, `IArmor` standardized across the engine.
- **New**: five stateless RPCs — `EquipItem`, `UnequipItem`, `AddItemToInventory`, `RemoveItemFromInventory`, `TransferItem` — give a downstream consumer its first real way to *change* a character's equipment/inventory after initial creation; previously `IEquipmentManager`/`IInventory` were real and tested in isolation, but nothing ever exposed them over gRPC, so nothing outside the engine itself could equip a found weapon, don armor, pick up loot, discard something, or hand an item to another character. `EquipItem` closes a real gap in `StandardEquipmentManager.Equip` itself (documented, ADR 0016): the manager doesn't verify the item is actually carried before equipping it, so the handler does that check before ever calling it. `TransferItem` explicitly ends attunement on the giving side first when the item being transferred is currently attuned (SRD: giving away an attuned item ends attunement) — `StandardInventory.RemoveItem`'s own existing auto-unequip-on-removal does not also do this. A shield equips into the same domain `OffHand` slot as an off-hand weapon (this engine has no separate `Shield` slot internally — `StandardEquipmentManager.EquipOffHandInternal` decides `.Shield` vs. `.OffHand` from the item's own type); the proto's `EQUIPMENT_SLOT_SHIELD` value exists purely so a caller can say "shield" rather than "off_hand". No quantity/stacking support — each item is a distinct inventory entry, matching this engine's existing model; "the party finds 5 torches" is 5 `AddItemToInventory` calls. Combat-loot distribution, death/inheritance handling, off-site possessions (mounts, stashes), and a buy/sell/vendor economy are real, deliberately separate follow-ons this closes the door to but does not itself build — `ILootGenerator`/`StandardLootGenerator` above remain otherwise unconnected to any distribution logic, and `IItem.Value` still has no reader anywhere.
- **New**: `ILootGenerator`/`StandardLootGenerator` finally get connected to something — a `GenerateLoot` RPC exposes them for the first time, and combining *multiple* creatures' challenge ratings into one group-appropriate roll (an evil high priest, three acolytes, and ten guards should net more total treasure than the priest alone, not be capped at his CR in isolation) is a brand-new `IEncounterChallengeCalculator`/`StandardEncounterChallengeCalculator`: the standard CR-to-XP conversion plus the standard monster-count XP multiplier, mapped back down to the single highest CR the resulting budget affords, which is what feeds `GenerateLoot`'s own existing, untouched tier logic. Deliberately lives on this side of the gRPC boundary rather than in a downstream consumer — this is game-specific encounter math, and a non-D&D system engine would have no equivalent concept at all. `GenerateLoot` takes `repeated Actor participants`, not a raw CR int, so a caller never computes or invents this number itself; every participant must resolve to a real creature carrying a real `challenge_rating` (a new field on `CreatureState`/`ICreature`, nullable rather than defaulting to 0 since 0 is itself a real, valid SRD CR — collapsing "never assigned one" into 0 would silently make an un-authored creature loot-eligible) or the whole call is rejected.
- **New**: real currency. `IInventory` gains `Copper`/`Silver`/`Gold`/`Platinum` plus `AddCurrency`/`RemoveCurrency` (mirroring `LootBundle`'s own four denominations), and `InventoryState` round-trips them the same additive, backward-compatible way every other optional `CreatureState` field already does. Two new RPCs land it on characters: `AddCurrency` (creation from nothing — a treasure placement) and `TransferCurrency` (moving currency from one creature's inventory to another's, mirroring `TransferItem`'s exact remove-then-add-with-real-rejection shape; fails if a requested denomination exceeds what's actually carried, and deliberately does not make change across denominations).
- **New**: `IItem.Value` finally gets a reader — line 16 above already flagged it as unused, and a downstream buy/sell/vendor economy pass needed real price data. Two new stateless RPCs: `GetItemInfo(item_name)` returns the real item library's price for a real item (an unrecognized name is a real rejection, same as `AddItemToInventory`), and `ListInventory(actor)` returns the real item names an actor currently holds (needed because `character_data` is opaque to the downstream Master consumer by design — it has no way to interpret the wire-format inventory shape itself). **Fixed alongside it, a genuine bug**: `Open5eItemMapper.ParseCost` previously mapped `Value` to whole gold pieces via integer truncation (its own comment read `// Convert to cp? Or keep as gold value? ... Let's assume Gold for now.`), so anything cheaper than 1 gp silently became `0` — a torch at "1 cp" priced as free. Since nothing read `Value` before this pass, this was invisible until now; `Value` is redefined as copper pieces (the finest SRD denomination, so every real price survives losslessly) and `ParseCost` fixed to match, with `IItem.Value` gaining the XML doc comment it never had explaining the unit. `GetItemInfo`'s response decomposes the price into the fewest coins (platinum first) so a caller can hand the result straight to `TransferCurrency`.
- **New**: `RemoveCurrency` — `AddCurrency`'s inverse, and the single-actor equivalent of `TransferCurrency`'s own remove-half. A downstream Layforge campaign-pack pass needed to debit an actor's currency into a location-scoped stash that isn't itself a creature, and `TransferCurrency` requires two real Actors on both ends — it can't express that. Same real rejection as `TransferCurrency`'s remove-half when a requested denomination exceeds what's actually carried.

### 🌐 Open5e Integration
- **Direct API Access**: Fetch Spells, Monsters, and Items directly from `api.open5e.com`.
- **Seamless Mapping**: Automatic conversion of Open5e JSON data to Engine DTOs.
- **New**: `Open5eItemCache`, mirroring `Open5eSpellCache` exactly, for the same real, live-observed reason — this file's own earlier entries said the item catalog was "small enough" to not need a cache; that turned out to be optimistic, since a later sidecar startup hit the 15-second `HttpClient` timeout fetching the full, paginated weapons+armor+magic-items catalog even with Open5e itself reachable. `Open5eContentSource` gained `GetAllWeaponDtosAsync`/`GetAllArmorDtosAsync`/`GetAllMagicItemDtosAsync` (splitting fetch from mapping, same as `GetAllSpellDtosAsync` already did for spells) so the cache can persist the raw DTOs, and `StandardItemLibrary.InitializeFromDtos` maps and loads them without ever touching the network — the sidecar's own cache-first/stale-fallback startup logic now mirrors the spell repository's exactly.
- **Fixed**: building that cache's own round-trip test surfaced a second, deeper instance of the exact bug class this repo already fixed once for `Open5eListResult<T>.Results` ("a get-only collection property is not reliably populated by `System.Text.Json` from a real HTTP response, with no exception thrown") — `Open5eWeapon.Properties` had the identical defect, one level deeper: `Results` itself now deserializes correctly, but every individual weapon inside it still silently kept an empty `Properties` list against the real Open5e API. Every weapon-property-dependent feature was quietly running on an empty list for any weapon actually fetched live from Open5e — `IWeapon.Range` parsing (an earlier "Fixed" entry in this same file), `Thrown`/`Ammunition` detection (`Attack`'s weapon-kind gating), and `TwoHanded` detection (`Grapple`'s free-hand check) all silently fell back to their SRD-default behavior instead of each weapon's real properties, for every live-fetched weapon, this whole time. Fixed the same way `Results` was: made `Properties` settable rather than get-only. Caught by a genuine JSON serialize/deserialize round-trip test (`Open5eItemCacheTests`) — every prior weapon test constructed `Open5eWeapon` directly in C#, which never exercises real deserialization at all, the same blind spot that let the original `Results` bug through.
- **Fixed since rc1**: the bulk *list* fetchers (`GetAllWeaponsAsync`/`GetAllArmorAsync`/`GetAllMagicItemsAsync`/the new `GetAllSpellsAsync`) share one generic `Open5eListResult<T>` type whose `Results` property was get-only — `System.Text.Json` silently left it empty against a real API response (scalar fields like `count`/`next` deserialized fine; only the results array was affected), with no exception thrown. Every prior test of this path used a mock constructed directly in C#, which never exercises real deserialization, so this went unnoticed. Found live while wiring the gRPC sidecar's spell repository; the fix (a settable property) applies to all four content types, not just spells.
- **Fixed since rc1**: `Open5eClient` is now retry-aware, and its timeout is *per attempt* (`Open5eRequestPolicy` — 4 attempts, 20s each, exponential backoff with jitter, honoring a `429`'s `Retry-After`). The earlier fix — a single 15-second `HttpClient.Timeout` — turned out to be the wrong knob: that budget covered the *whole* ~14-page paginated spell fetch (plus a separate weapons+armor+magic-items pull), so two or three slow pages against Open5e's Cloudflare front exhausted it and the whole fetch threw. A downstream Layforge self-hoster hit exactly that on a clean clone — `failed to populate spell repository … no local cache exists`, with nothing to fall back on. `Open5eClient` now rides out the transient failures (a timed-out attempt, a connection error, `429`/`5xx`) instead; only a genuinely unreachable Open5e — every attempt failing — throws, now a dedicated `Open5eUnavailableException` that the bulk list fetchers deliberately let propagate (a half-fetched SRD list must not be cached as if complete) while single-slug lookups still swallow into `null`. The sidecar's `HttpClient.Timeout` is back to `InfiniteTimeSpan` so it can't re-impose a shorter whole-fetch cap, and its cold-cache failure message now names `OPEN5E_SPELL_CACHE_PATH`/`OPEN5E_ITEM_CACHE_PATH` as the recovery.
- **New**: the gRPC sidecar (`OpenCombatEngine.GrpcSidecar`) now populates a real `ISpellRepository` from this integration at startup, so `spellcasting` (known/prepared spells, slots) actually survives the gRPC round trip — previously always `null` regardless of what was sent in, for every creature, on every RPC that reconstructed one.
- **New**: a `CastSpell` RPC exposes the already-tested `CastSpellAction` (checks `PreparedSpells`, with correct fallback to `KnownSpells` for a non-prepared caster; checks/consumes a slot; rolls the target's real saving throw) over gRPC for the first time — previously reachable only from within the engine itself, never from a downstream consumer like Layforge.
- **New**: `CastSpellRequest` gained an optional `grid_context` field (caster/target positions plus line-of-sight-blocking cells) so `CastSpellAction`'s own range/line-of-sight check — already written, already tested, but silently dormant since nothing ever constructed a populated `IGridManager` for it — finally receives real data. `StandardGridManager` needed no changes at all: its `GetDistance` already returns Chebyshev distance × 5 (feet, 5-ft squares), the exact convention the calling side (Layforge's own generated combat map) already uses, so positions cross the gRPC boundary with zero unit conversion. Omitting `grid_context` (the default — no combat map exists for a given cast) behaves exactly as before this field existed; this is additive, not a breaking change to `CastSpell`'s existing behavior. Real per-cell cover computation remains genuinely unbuilt (`IGridManager` has no such method at all) and is not part of this — `CoverType` stays real only where `StandardCreature.ResolveAttack` already used it directly.
- **New**: a local on-disk cache (`Open5eSpellCache`) for the sidecar's startup spell fetch — real problem found live during this project's own development: repeatedly restarting the sidecar during local testing hammered Open5e's API enough to get this environment rate-limited/blocked by Open5e's own Cloudflare front, leaving the sidecar unable to start (or start quickly) at all. Startup now checks a local cache (`OPEN5E_SPELL_CACHE_PATH`, default next to the binary) first and skips the live fetch entirely if it's fresh (age-based staleness, 7-day default — SRD content is static enough that a conditional-request/ETag scheme would just be network round trips spent to learn "nothing changed"); a live fetch that does happen writes the cache for next time; a live fetch that fails falls back to a stale cache rather than starting with zero spells. `HttpClient`'s startup timeout was also tightened from the 100-second default to 15 seconds, so a genuinely unreachable Open5e fails into the cache fallback quickly instead of leaving the process looking hung.
- **Fixed**: `Open5eAdapter.ToStandard(Open5eSpell)` never populated `SpellDto.Damage`/`DamageInflict`/`SavingThrow` — and Open5e's own REST API doesn't expose those as separate structured fields for spells, only as prose inside `desc` (e.g. "3d4 + your spellcasting ability modifier force damage"). Net effect: every spell sourced from this integration dealt **zero** damage when cast via `CastSpellAction`, regardless of what its real SRD description said — confirmed live via `CastSpell`, not assumed. Fixed with a new `Open5eSpellTextParser` that recovers damage dice/type and saving-throw ability from the SRD's own consistent phrasing ("takes XdY &lt;type&gt; damage", "&lt;ability&gt; saving throw") — best-effort prose parsing, not a full NLP solution, but it covers the standard phrasing every sampled SRD spell (Magic Missile, Fireball, Sacred Flame, Poison Spray, and others) actually uses.
- **Fixed**: three follow-up gaps found alongside the one above, all now closed —
  - **Healing.** `SpellMapper.MapHealingDice` was a permanent stub that always returned `null`, regardless of spell source (not an Open5e-specific bug, but the same class of "the field exists on `ISpell` and nothing ever populates it" gap). `Open5eSpellTextParser` now also extracts a healing spell's dice from "regain[s]/restore[s] ... hit points [equal to XdY]" phrasing (Cure Wounds' "regains ... hit points equal to 1d8 + your spellcasting ability modifier" → `"1d8"`; the ability-modifier suffix is dropped, same simplification damage dice already accept, since `HealingDice` is a fixed string with no caster-dependent bonus).
  - **Attack rolls.** `SpellAttack`/`RequiresAttackRoll` was never populated, and even when set, `CastSpellAction` never branched on it — an attack-roll spell (Ray of Frost, Scorching Ray, Guiding Bolt, Inflict Wounds, Chill Touch) always hit and dealt full damage, the same "auto-hit" bug the save-based fix above closed for save spells. `Open5eSpellTextParser` now detects the SRD's "Make a melee/ranged spell attack" phrasing, and `CastSpellAction` now actually rolls 1d20 + proficiency + casting ability modifier against the target's own armor class (natural 20 always hits, natural 1 always misses, no crit-damage-doubling yet) before applying that instance's damage.
  - **Multi-instance spells.** Magic Missile's three darts, Scorching Ray's three rays — each independently rolled per SRD — previously only ever resolved as a single instance, since the only multiplier `CastSpellAction` had was cantrip level-scaling (Level 0 only). New `ISpell.InstanceCount`/`InstanceCountPerUpcastLevel` members (default 1/0 — no effect on the overwhelming majority of spells) are populated from "you create &lt;count&gt; ... darts/rays/..." and "one more/additional ... for each slot level above" phrasing, and `CastSpellAction`'s damage loop now rolls (and, for an attack-roll spell, independently attack-rolls) each instance separately — a miss on one ray no longer blocks or reduces the others.
- **New**: an `Attack` RPC exposes the already-tested `AttackAction` (real attack roll, advantage/disadvantage from conditions and flanking, crits, range/LOS) over gRPC for the first time — previously the only way a martial character's attack could be resolved was Layforge's `apply_effect`, which has no weapon-legality or range/LOS concept at all. The engine checks the attacker's actual equipped main-hand weapon and rejects the call when it can't do what's being asked: an `AttackKind.Ranged` request against a weapon with neither `Thrown` nor `Ammunition` (a longsword), or `AttackKind.Melee` against an `Ammunition`-only weapon (a bow) — a real mechanical gate on the weapon's own SRD properties, not a per-kind allowlist.
- **Fixed**: `IWeapon` had no numeric range at all, despite Open5e's own weapon `properties` strings already carrying one — `"thrown (range 20/60)"` — that `Open5eItemMapper.ParseWeaponProperties` silently discarded by keeping only the leading word (`"thrown"`). `IWeapon.Range` (feet) is now real, parsed from that same text, with an SRD-accurate fallback (10 ft for `Reach`, 5 ft otherwise) only when a weapon's properties carry no range text at all — same "parse real Open5e data, don't hardcode a table" principle as `Open5eSpellTextParser`.
- **Fixed**: a second, more consequential instance of the same "real data silently dropped" bug class as the spellcasting-always-`null` fix above — `ActorMapping.ToCreature` (the Layforge gRPC sidecar's Actor↔creature converter) never had a real `IItemLibrary` to resolve inventory item names back into live weapon/armor objects, so `StandardCreature.ResolveItem` always fell back to a bare placeholder `StandardItem` — not an `IWeapon` — meaning **every equipped weapon silently came back unequipped after a gRPC round trip**, regardless of what a character actually had equipped, for every RPC that reconstructs a creature (not just the new `Attack` RPC). `ActorMapping.ToCreature` gained an optional `itemLibrary` parameter, and the sidecar (`Program.cs`) now builds and populates a real `StandardItemLibrary` from Open5e's weapon/armor/magic-item endpoints at startup, alongside the spell repository, and injects it into `SystemEngineGrpcService`.
- **New**: a `GetAvailableActions` RPC computes the full concrete list of mechanically legal actions a character can take right now — every equipped-weapon attack option (melee, ranged, and now a genuinely new off-hand/secondary-weapon bonus-action attack per SRD Two-Weapon Fighting), Grapple and Shove options, and every currently-castable prepared/known spell, each against every candidate target supplied by the caller — rather than leaving the caller to guess or trial-and-error against `Attack`/`CastSpell`. Building this surfaced that `ICreature.Actions` (which looked like a ready-made menu) actually under-represents a player character's real options — it only ever yields a hardcoded "Unarmed Strike" for equipped-weapon attacks, completely ignoring `Equipment.MainHand`/`OffHand` — so `GetAvailableActions` derives weapon options directly from equipment instead, the same way `Attack`'s own handler already did (now shared via `WeaponAttackRules`, extracted from `Attack`'s handler so the two can't drift into different answers for the same weapon).
- **New**: `GrappleAction` and `ShoveAction` — real SRD mechanics that did not exist anywhere in this engine before (only the resulting `Grappled`/`Prone` conditions existed; nothing ever applied them). Both are an opposed check (source's Strength (Athletics) against the target's better of Athletics/Acrobatics) built entirely from already-tested primitives (`ICheckManager.RollAbilityCheck`, `ConditionFactory`/`Conditions.AddCondition` — the same pattern `RageAction` already used — and, for Shove's push, `IGridManager.MoveCreature`). Grapple requires a free hand, approximated from real equipped-weapon data (`Equipment.OffHand`/`Shield` empty, `MainHand` not `WeaponProperty.TwoHanded`) since this engine doesn't model creature size or a dedicated "hand" concept beyond what's inferable from equipment. Neither models creature Size (SRD's "no more than one size category larger" restriction) — genuinely unmodeled anywhere in this engine, a documented simplification, not an oversight.
- **New**: a real source-side incapacitation gate (`IncapacitationCheck`) — before this, `AttackAction`/`CastSpellAction` only ever checked a *target's* Paralyzed/Stunned/Petrified conditions (for advantage); nothing checked whether the creature *attempting to act* was itself incapacitated. Now a real precondition on `AttackAction`, `CastSpellAction`, `GrappleAction`, and `ShoveAction` alike, and the same fact `GetAvailableActionsResponse.can_act` reports — deliberately independent of the HP-based Unconscious/Dying/Dead status (`StartTurn`'s automatic death save continues to work exactly as before; a downed character still gets their turn to roll it).
- **New**: `GetAvailableActions` can now actually be *acted on*, not just advertised — the same-release follow-up closing the gap the first cut of this feature deliberately flagged rather than shipped silently: `Attack` gained a third kind, `ATTACK_KIND_OFFHAND` (resolves against `Equipment.OffHand`, always a bonus action, never adds the ability modifier to damage per SRD Two-Weapon Fighting's core rule), and two new RPCs, `Grapple` and `Shove`, expose `GrappleAction`/`ShoveAction` over gRPC for the first time — mirroring `Attack`'s own stateless, grid-context-aware shape (a shared `BuildGridFromContext` helper now backs both, alongside `Attack`/`CastSpell`'s own inline versions, deliberately left untouched since they're already tested).
- **Found, flagged, not fixed (out of scope for this pass)**: `StandardEquipmentManager.Equip` unequips an item from any other slot before equipping it into a new one (a same-physical-item, reference-identity check) — combined with `StandardItemLibrary`/a content-backed `IItemLibrary` handing out one shared instance per item name for non-magic items, dual-wielding two of the *exact same* named weapon (e.g. twin daggers from the same content source) silently steals the item back out of the first hand instead of equipping both. Discovered incidentally while testing off-hand attacks; a real, pre-existing engine limitation, not introduced by this release.

### 💾 Persistence & State
- **Full Serialization**: Save and Load combat encounters to JSON.
- **Resilient Restoration**: Win conditions and event subscriptions persist across save/load cycles.

### 🧙 Character Creation
- **New**: `ICharacterCreationService`/`StandardCharacterCreationService` — a genuinely new kind of engine surface, the first *stateful* System Engine RPC in this project (every other RPC is stateless per-call): `StartCharacterCreation`/`AnswerCharacterCreationPrompt` drive an in-memory, ephemeral (lost on restart by design, no persistence layer for it yet) question-sequence session keyed by a caller-generated `session_id`, deciding the next question purely from what's been answered so far rather than a fixed step list a downstream caller would otherwise have to hardcode. Curated SRD 5.1 data, hand-authored rather than sourced from Open5e (whose API has no races/classes/backgrounds endpoints): 4 races (Human, Elf, Dwarf, Halfling), 4 classes (Fighter, Wizard, Cleric, Rogue), 4 backgrounds (Acolyte, Criminal, Folk Hero, Soldier), 2 ability-score methods (standard array, 4d6-drop-lowest), fixed one-kit-per-class starting equipment, no subclass selection (irrelevant at level 1 for any of the four).
- **New**: a single `CharacterCreationMode` (`QUICK`/`DETAILED`) flag controls how many steps the *same* sequence surfaces rather than branching into two separate generators — quick mode asks exactly three real questions (race, class, gender) then auto-rolls background/ability-score assignment/spell picks internally using the identical decision logic detailed mode exposes as real prompts, so the two can never silently drift into different generation rules.
- **New**: a level-1 Wizard or Cleric is a real SRD spellcaster the moment creation finishes — 3 cantrips, 2 first-level slots, and prepared/known spells equal to ability modifier + level (minimum one) — chosen from the same live `ISpellRepository` every other spell-aware RPC already uses (real, class-tagged Open5e data via a new `Classes` property on `ISpell`, added as a C# 8 default interface member so no existing test fake needed changes), never a second, sync-prone hand-authored spell list.
- **New**: `CreatureState`/`ICreature` gain an optional `Gender` field — purely cosmetic, no SRD mechanical effect, additive per this project's own backward-compatible-optional-field convention.
- **Fixed since rc1**: the gender creation prompt sent an empty choice list, so a downstream client (Layforge) rendered it as a free-text box — the wrong control. It now offers a fixed **Male / Female** choice list and rejects anything else, case-normalized like the race/class/background prompts already were.
- **New**: `Actor.level` — a real top-level field on the gRPC contract's `Actor` message, populated in `ActorMapping.ToActor` as `creature.LevelManager.TotalLevel` (already a real property — the sum of every class level for a multiclass character, no new engine logic needed). Exists specifically so a downstream consumer (Layforge's new character-import review flow) can read a character's level without parsing `character_data`'s engine-specific shape itself — the same reasoning `challenge_rating` was added for earlier. 0 means "no class levels to report" (e.g. a pure-CR monster stat block), never a real level.

- **Test Coverage**: 751 Unit and Integration tests passing — every project, including `Open5eIntegrationTests` (the 3 tests that intentionally hit the real Open5e API rather than a mock). Those 3 genuinely failed with socket/TLS timeouts partway through this release's own development, for real: Open5e's API became unreachable from this environment for a stretch — almost certainly the exact rate-limiting/blocking problem `Open5eSpellCache` (above) exists to make survivable — and passed again once connectivity returned, confirmed on a second full run. Not a regression from any change in this release, but real, live-observed evidence for why the new cache exists.
- **End-to-End Verified**: Full "Mock Battle" scenarios run successfully, validating the interaction of all systems.
- **Spellcasting round trip verified live** against the real Open5e API and a real downstream consumer (Layforge's Master + a real LLM): a character with a spell known-but-not-prepared, and another prepared, correctly distinguished the two through the gRPC sidecar.
- **`CastSpell` verified live** against the real Open5e API, the gRPC sidecar, and a real downstream consumer (Layforge's Master + a real LLM, `qwen3.8:27b`): a known-but-unprepared spell was hard-rejected by the engine (not just narrated as failing), and a prepared spell with an available slot succeeded — both surfaced correctly through Layforge's `cast_spell` DM tool.
- **Damage/healing/multi-instance fixes verified live**, same stack: a prepared Magic Missile cast dealt 8 damage (three independently-rolled 1d4+1 darts, consistent with a real 3-instance roll rather than one), and a prepared Cure Wounds cast raised the caster from 10/18 to 16/18 HP (a real 1d8 roll, persisted). Attack-roll gating (Ray of Frost/Scorching Ray-style) is covered by 9 new deterministic-dice unit tests rather than a live run — a live LLM session can't control which d20 a hit/miss test needs, so this one is unit-only, not silently claimed as live-verified.
- **Spell cache verified live** against a real sidecar, two full startup cycles: the first, with no cache present, fetched all 1435 spells live from Open5e and wrote the cache (~20s); the second, immediately after with the same cache file, loaded all 1435 spells from disk in ~4s and logged that it skipped the live fetch entirely.
- **`Attack` verified live** against the real Open5e API (1709 real SRD weapons/armor/magic items loaded into a real `StandardItemLibrary` at sidecar startup), the gRPC sidecar, and a real downstream consumer (Layforge's Master + a real LLM, `qwen3.8:27b`): a character with a real equipped Longsword called `melee_attack`, the engine rolled a real attack and dealt real damage against a goblin NPC (7 HP down to barely conscious), and the mutated state persisted on both sides — proving the full chain (Open5e → `IItemLibrary` → `ActorMapping` → `AttackAction`) works end to end, including the `ActorMapping`/`IItemLibrary` fix above, which this attack could not have succeeded without. The weapon-kind *rejection* path (a Shortbow-equipped character asked to attack in melee) was attempted live twice; both times the DM model narrated a plausible-sounding refusal on its own judgment without ever calling `melee_attack` — a real finding, reported honestly rather than claimed as a live engine rejection. That branch is instead covered by deterministic gRPC-layer tests (`Attack_MeleeAttackWithBowEquipped_ReturnsFailure`, `Attack_RangedAttackWithLongswordEquipped_ReturnsFailure`, `Attack_NoWeaponEquipped_ReturnsFailure`) plus the weapon-range-parsing tests in `Open5eItemMapperTests.cs` and the round-trip regression pair in `ActorMappingTests.cs`.
- **`GetAvailableActions` and the turn-order incapacitation gate verified live** against a real sidecar and a real LLM (`qwen3.8:27b`) — with one honest asterisk: Open5e was genuinely unreachable during this verification run (confirmed via direct `curl` timeouts against `api.open5e.com`), so the sidecar's item library never populated and the weapon-*dependent* options (melee/ranged/off-hand) could not be exercised live this time; that path is covered instead by the deterministic `GetAvailableActions_*` suite in `SystemEngineGrpcServiceTests.cs`.
